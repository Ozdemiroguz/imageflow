# Realtime — Native Boundary & Layering

> The question: "why do framework-less services still sit in a flat `realtime/services/`, and shouldn't we be *managing the native types* properly?" This doc answers it with **evidence from the code + primary sources**, then gives the concrete plan.
>
> **Headline finding:** the native *boundary* in `realtime` is **already mostly correct** — raw `CameraImage`/`Face`/`InputImage` stay in the detection/conversion code and the **results that cross into presentation are already plugin-free domain types** (`Rect`, `Offset`, `NormalizedCorners`, `Uint8List`). The real defect is **folder layering** (a flat `services/`), **not** type leakage. So the fix is to *move files into `data/` + `presentation/`*, not to wrap every frame.

**Date:** 2026-06-30 · Companion to [SERVICE_PLACEMENT.md](./SERVICE_PLACEMENT.md), [LAYERING_REVIEW.md](./LAYERING_REVIEW.md).

---

## 1. The rule (from primary sources)

**Raw framework types may live in the data layer; only *results* cross the boundary as domain types — never into domain entities or presentation.**

- Uncle Bob — *"Data formats used in an outer circle should not be used by an inner circle, especially if those formats are generated by a framework... we don't want to cheat and pass Entities or [framework] rows... [pass] simple data structures... in the form most convenient for the inner circle."* ([Clean Architecture](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)) → the *result* crossing inward must be a plain domain structure; the framework type stays out.
- Official Flutter — *"Services are in the lowest layer... They wrap API endpoints and expose `Future` and `Stream` objects... Repositories... transform that raw data into **domain models**."* and *"the service is a **private member**, so the UI layer can't... call a service directly."* ([data layer](https://docs.flutter.dev/app-architecture/case-study/data-layer), [guide](https://docs.flutter.dev/app-architecture/guide)) → the plugin-wrapping "Service" is a **data-layer** class; the raw type is private to it.
- Code With Andrea — wrap the SDK so *"the calling code will only ever use types... **we have defined**"*, holding the third-party object *"as a private variable."* ([abstraction & repository](https://codewithandrea.com/articles/abstraction-repository-pattern-flutter/)) → ACL: foreign type private, domain type out.
- Microsoft ACL — *"the anti-corruption layer contains all the logic necessary to translate between the two systems,"* and explicitly extends to *"asynchronous, event-driven... high-throughput workloads"* ([ACL pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/anti-corruption-layer)) → the boundary applies to a **streaming** frame source too.

**Performance caveat (also sourced):** the official Flutter recommendations mark *"create separate API models and domain models"* as **conditional** ("use in large apps") — not an absolute. So **per-frame wrapping of `CameraImage` into a domain DTO is *not* required**; converting **once** inside the data-layer detector and emitting domain results is the correct, non-over-engineered choice.

> **The decisive litmus:** `CameraImage`/`InputImage`/`Face` are *allowed as parameters/locals inside `data/`* — they are **forbidden** in `domain/` and `presentation/`.

## 2. What the code actually does (measured)

| Concern | Status | Evidence |
|---|---|---|
| Does the **overlay state** (what presentation reads) hold plugin types? | ✅ **No** — plugin-free | `realtime_overlay_state_store.dart`: `List<Rect>`, `List<List<Offset>>`, `Rxn<NormalizedCorners>`, `Rxn<Uint8List>`. No `Face`/`CameraImage`. |
| Is there a **translation step** `Face → domain`? | ✅ **Yes** | `realtime_face_geometry_normalizer.dart`: takes ML-Kit `Face`, returns `Rect`/`List<Offset>` (normalized 0–1). This *is* the ACL translator. |
| Do presentation **widgets** touch `Face`/`CameraImage`? | ✅ **No** (one benign exception) | Only `realtime_page_camera_preview.dart` imports `camera` — for the official `CameraPreview` widget, which is the sanctioned way to show the feed. No widget processes `Face`/`CameraImage`. |
| Where do `CameraImage`/`InputImage` live? | 🟡 **In the detection/conversion classes** | `realtime_face_detection_service`, `realtime_ocr_gate_service`, `realtime_preview_builder`, `realtime_detection_pipeline_coordinator`, the `realtime_input_image_factory`. Per the rule, **this is the correct place** — *if those classes are in `data/`.* |
| Are those classes in `data/`? | ❌ **No** — flat `realtime/services/` | This is the actual defect. |

**Conclusion:** the boundary is sound — raw frame types are confined to the conversion/detection layer and only domain types (`Rect`/`Offset`/`NormalizedCorners`/bytes) reach presentation. The codebase is **not** leaking `Face`/`CameraImage` into domain or widgets. What's wrong is that the data-layer classes are mis-foldered as flat `services/`, so the layering doesn't *show* the boundary that actually exists.

## 3. Target shape (move, don't translate)

Reclassify `realtime/services/` by the import litmus ([SERVICE_PLACEMENT §1](./SERVICE_PLACEMENT.md)):

```
features/realtime/
├── data/
│   ├── datasources/
│   │   ├── realtime_face_detection_service.dart   (wraps ML-Kit FaceDetector)
│   │   └── realtime_ocr_gate_service.dart          (wraps ML-Kit TextRecognizer)
│   └── services/
│       ├── realtime_preview_builder.dart (+payloads) (camera+image → preview bytes)
│       ├── realtime_detection_pipeline_coordinator.dart (orchestrates detection; converts Face→domain)
│       ├── realtime_face_geometry_normalizer.dart   (the ACL translator; pure-ish)
│       └── realtime_frame_perf_tracker.dart         (pure)
└── presentation/
    ├── coordinators/
    │   ├── realtime_camera_session_coordinator.dart (camera+GetX+Rx state)
    │   └── realtime_stream_coordinator.dart          (camera+GetX+Rx state)
    ├── state/ (already here: realtime_overlay_state_store.dart)
    ├── controllers/ pages/ widgets/ models/ enums/
```

**On domain interfaces — the honest answer to "make it like processing":**
- Processing's detectors are plugin-free because they take a **path** and return a **domain `DetectionResult`** — fully translatable.
- Realtime's detectors take a **`CameraImage`** and (for face) return ML-Kit `Face`. Their *public signatures inherently carry plugin types* on the **input** side. Per the rule, that's **fine in `data/`** — but a `domain/services/` interface for them would have to import `camera`/`google_mlkit`, which **violates** "domain is framework-free" ([SERVICE_PLACEMENT §1](./SERVICE_PLACEMENT.md)).
- **Therefore: do NOT add domain interfaces for the frame-consuming detectors.** Forcing them would push plugin types *into* `domain/` — strictly worse than leaving them as concrete data-layer services. This is a **justified asymmetry** with processing (batch-path vs live-frame), not an inconsistency to "fix."
- The detectors already accept an injectable `FaceDetector?`/`TextRecognizer?`/`MethodChannel?` for testing, so the test seam exists without a plugin-importing interface.

> **One real translation improvement worth doing (optional, separate):** `realtime_face_detection_service.detect` currently returns `List<Face>` (ML-Kit). It *could* return a domain face type so `Face` stops appearing in the coordinator. But the normalizer already converts `Face → Rect/Offset` immediately downstream, so `Face` never reaches presentation today. This is a *nice-to-have purity tweak*, not a boundary fix — deferred unless wanted.

## 4. Plan (move-only; behavior-preserving)

1. Create `realtime/data/datasources/`, `realtime/data/services/`, `realtime/presentation/coordinators/`.
2. `git mv` each file to its layer per §3; fix the relative imports (depth changes).
3. Update importers (controller, stream coordinator, binding) to the new paths.
4. `flutter analyze` clean + 188 tests green after each move.
5. Update [SERVICE_PLACEMENT.md](./SERVICE_PLACEMENT.md): change the "flat `realtime/services/` is a documented legacy convention" note to "resolved — realtime now layered."

**Not doing:** per-frame `CameraImage`→DTO wrapping (over-engineering, perf cost, no payoff — the boundary already holds); domain interfaces for frame-consuming detectors (would leak plugin types into `domain/`).

## 5. One-paragraph answer

You were right to push on it — but the investigation shows the **native types are already managed correctly at runtime**: `CameraImage`/`Face`/`InputImage` are confined to the detection/conversion classes, results are translated to `Rect`/`Offset`/`NormalizedCorners` before they reach the overlay state, and **no presentation widget or domain entity touches a plugin type**. Primary sources (Uncle Bob, official Flutter, Code With Andrea, Microsoft ACL) all agree that a framework type may live *inside the data layer* as long as only domain results cross the boundary — which is exactly what happens here. So the fix is **folder layering** (move the flat `services/` into `data/` + `presentation/`), **not** wrapping every frame. Adding plugin-free domain interfaces for the frame-consuming detectors would be *wrong* — it'd force `camera`/`ml_kit` imports into `domain/`. The asymmetry with processing (which is fully plugin-free) is justified: batch works on paths, realtime works on live frames.
